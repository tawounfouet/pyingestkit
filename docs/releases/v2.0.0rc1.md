# PyIngestKit 2.0.0rc1

## Status

**Release candidate — LOT-21.**

This candidate promotes the clean-slate V2 architecture into the actual package
root. It is not a compatibility alias release for the V1 Job/Pipeline/Step
runtime.

## Public root freeze

The candidate root is intentionally small:

```python
from pyingestkit import (
    ArtifactReference,
    DatasetVersion,
    DatasetVersionReference,
    IngestionDefinition,
    IngestionResult,
    IngestionRun,
    IngestionRunId,
    IngestionRuntime,
    PublishedDataset,
    ResourceReference,
    Source,
)
```

The canonical execution entry point is `IngestionRuntime.run(...)`.

## Release-candidate evidence

LOT-21 requires all of the following before merge:

- Python 3.11–3.14 qualification;
- architecture and public-contract tests;
- stable Protocol signature freeze;
- provider conformance for local, HTTP, PostgreSQL and S3-compatible storage;
- canonical serialization and migration fixtures;
- publication uncertainty/reconciliation tests;
- clean wheel and source-distribution installation;
- optional-provider isolation;
- PyTransformKit 1.1.0 integration evidence;
- Customer 360 built-artifact execution;
- Ruff, formatter, mypy and security gates;
- migration guidance and known limitations.

## Breaking changes from 1.x

PyIngestKit 2.0 deliberately removes V1 execution aliases from the package
root. Applications using `Job`, `Pipeline`, `Step`, `Runner`,
`RunContext`, `job` or `step` must either remain pinned to the 1.x line or
migrate to `IngestionDefinition` + `IngestionRuntime`.

V1 semantic migration tooling remains available under
`pyingestkit.migration`; this is conversion tooling, not an execution shim.

## Known limitations

- The V1 Job/Pipeline/Step CLI/plugin runtime is not a 2.0 public execution
  contract. The 2.0 RC is qualified primarily as a Python framework API.
- PyTransformKit is a sibling optional integration. RC qualification pins the
  validated 1.1.0 implementation commit explicitly rather than silently
  accepting arbitrary sibling versions.
- V2 currently standardizes CSV/JSON(L) decoding and the providers already
  covered by the V2 conformance matrix. Legacy V1 parser/runtime modules may
  remain in the source tree for migration history but are not part of the 2.0
  compatibility promise.

## Stable promotion rule

After this RC is accepted, only blocker fixes are permitted before 2.0.0.
Any architectural redesign or stable API/Protocol reshaping resets the RC.
