# PyIngestKit 2.0.0

## Status

**Stable — LOT-22.**

PyIngestKit 2.0.0 promotes the fully qualified 2.0.0rc1 contract without
architectural redesign. The package root, runtime method, provider Protocols and
portable wire-contract versions remain identical to the release candidate.

## Stable public root

```python
from pyingestkit import (
    ArtifactReference,
    DatasetVersion,
    DatasetVersionReference,
    IngestionDefinition,
    IngestionResult,
    IngestionRun,
    IngestionRunId,
    IngestionRuntime,
    PublishedDataset,
    ResourceReference,
    Source,
)
```

The canonical synchronous entry point is `IngestionRuntime.run(...)`.

## Stable guarantees

- V1 `Job / Pipeline / Step / Runner` aliases are not part of the 2.0 root.
- RAW remains durable immutable ingestion evidence.
- Artifact storage, dataset-version storage and target materialization remain
  semantically distinct.
- DatasetVersion is immutable governed identity.
- write and publish are distinct operations.
- publication uncertainty and reconciliation remain explicit.
- replay allocates a new `IngestionRunId` and does not silently reacquire a source.
- base installation remains provider-neutral.
- portable serialization is versioned and non-executable.
- PyTransformKit integration remains optional and reference-based.
- V1 migration remains explicit rather than alias-driven.

## Wire contracts

All stable portable boundary contracts ship at contract version `1`.
Their exact IDs and versions are recorded in
`tests/contract/fixtures/stable_release_v2.json` and
`tests/contract/fixtures/v2_boundary_values.json`.

## Qualified providers

See `docs/reference/provider-compatibility-v2.md` for the support matrix.

The stable qualification includes local/filesystem providers, HTTP acquisition,
PostgreSQL 16 targets, S3-compatible artifact/version stores, clean built
artifacts, PyTransformKit integration and Customer 360.

## Migration

Applications using the V1 execution model should remain on the 1.x line until
they are semantically migrated. See `docs/guides/migrate-v1-to-v2.md`.

## Qualification and publication

The stable qualification procedure is documented in
`docs/releases/v2.0.0-qualification.md`.

The `v2.0.0` tag is created only after the exact stable merge SHA passes
post-merge CI, Security and Docs.
