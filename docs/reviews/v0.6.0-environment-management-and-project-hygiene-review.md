# Review: V0.6.0 Environment Management, Project Hygiene & Observability

## Overview

Ce document retrace la réorganisation de la gestion des variables d'environnement, le renforcement de la sécurité anti-fuite de secrets, et l'optimisation de l'observabilité/journalisation (DX) dans **PyIngestKit V0.6.0**.

---

## 1. Problématiques Initiales

### Encombrement et confusion à la racine du projet
Au fil des itérations, la racine du package `pyingestkit-v0.6.0` s'est retrouvée encombrée de multiples fichiers d'environnement masqués :
`.env`, `.env.example`, `.env.dev`, `.env.dev.example`, `.env.stg.example`, `.env.staging.example`, `.env.prod.example`.
Cette dispersion présentait plusieurs risques :
- **Risque de fuite de secrets** : Risque d'omettre l'un des fichiers dans le fichier `.gitignore` et de pousser des identifiants sensibles vers un dépôt public.
- **Friction cognitive** : Ambiguïté pour le développeur sur le fichier d'environnement effectivement pris en compte lors de l'exécution d'une commande `pyingest`.

### Logs temps-réel masqués dans la console
Lors de l'utilisation de certaines configurations par défaut, les logs d'étapes (INFO, DEBUG) ne s'affichaient pas en direct sur la console, ne laissant apparaître que le bandeau récapitulatif final de Rich.
- **Cause identifiée** : La directive `logging.console` était positionnée à `false` dans certains templates, n'activant que le fichier journal sur disque.

## 3. Détection Dynamique de l'Environnement (`PYINGEST_ENV`)

Le point d'entrée du CLI ([src/pyingestkit/cli/main.py](file:///Users/awf/workspace/professionnal/webtech/clients/prepavogt-alumni/packages/pyingestkit-v0.6.0/src/pyingestkit/cli/main.py)) a été enrichi pour inspecter la variable `PYINGEST_ENV` :

```python
def _load_local_dotenv() -> None:
    """Load the working-directory environment file without overriding OS variables."""
    import os

    env_name = os.getenv("PYINGEST_ENV")
    if env_name and env_name.strip():
        name = env_name.strip()
        candidates = (
            Path.cwd() / "envs" / f".env.{name}",
            Path.cwd() / "envs" / f".env.{name}.example",
            Path.cwd() / f".env.{name}",
        )
        for target in candidates:
            if target.exists():
                load_dotenv(dotenv_path=target, override=False)
                break

    load_dotenv(dotenv_path=Path.cwd() / ".env", override=False)
```

Grâce à cette amélioration :
- L'utilisateur peut préfixer ses commandes sans toucher aux fichiers :
  ```bash
  PYINGEST_ENV=dev pyingest runs
  PYINGEST_ENV=stg pyingest runs
  ```
- Ou continuer d'utiliser le workflow standard en copiant le fichier souhaité :
  ```bash
  cp envs/.env.dev.example .env
  ```

## 4. Observabilité & Logging Standardisé

### Clarification des modes de journalisation
Dans les trois profils de configuration (`pyingest.yml.dev`, `pyingest.yml.stg`, `pyingest.yml.prod`), la politique de journalisation a été explicitée :

| Environnement | `logging.console` | `logging.format` | Objectif |
|---|---|---|---|
| **Dev** | `true` | `rich` | Expérience développeur interactive, diagnostic immédiat |
| **Staging** | `true` | `rich` | Validation visuelle des flux avant expédition |
| **Prod** | `true` | `plain` | Format texte horodaté standard collectable par Fluentd / Datadog |

En complément, chaque profil active la journalisation persistante sur disque dans `.pyingest/logs/pyingest.log` au format **JSON structuré** avec rotation automatique (10 Mo x 5 fichiers), garantissant une traçabilité et un audit post-mortem complets des runs d'ingestion.
