# Review: V0.6.0 Multi-Environment Profiles & Cloud Object Storage (S3 / MinIO / R2)

## Overview

Ce document détaille la formalisation des profils de déploiement multi-environnements (**Dev**, **Staging**, **Production**) ainsi que la qualification opérationnelle du stockage d'artéfacts immuables sur **S3**, **MinIO** et **Cloudflare R2** dans **PyIngestKit V0.6.0**.

---

## 1. Architecture des Profils de Configuration

Afin d'adapter PyIngestKit aux différentes étapes du cycle de vie logiciel sans modifier le code source des pipelines, trois profils YAML officiels ont été établis :

### A. Profil Développement Local : [pyingest.yml.dev](file:///Users/awf/workspace/professionnal/webtech/clients/prepavogt-alumni/packages/pyingestkit-v0.6.0/pyingest.yml.dev)
- **Objectif** : Zéro dépendance réseau/cloud, itération ultra-rapide pour le développeur.
- **Stockage d'artéfacts** : `backend: local` (système de fichiers dans `.pyingest/artifacts/`).
- **Métadonnées d'exécution** : `backend: sqlite` (fichier local `.pyingest/state/pyingest.sqlite3`).
- **Mode fixtures** : `fixture_mode: true` (rejeu offline sans requêtes HTTP externes).
- **Journalisation** : `format: rich` (interface console enrichie, couleurs, barres de progression) + log local en JSON.

### B. Profil Staging / Docker Compose : [pyingest.yml.stg](file:///Users/awf/workspace/professionnal/webtech/clients/prepavogt-alumni/packages/pyingestkit-v0.6.0/pyingest.yml.stg)
- **Objectif** : Validation intégrée ISO-production sur environnement local ou serveur d'intégration continue via Docker Compose.
- **Stockage d'artéfacts** : `backend: s3` pointant vers une instance **MinIO** locale (`endpoint_url_env: PYINGEST_S3_ENDPOINT_URL`, ex: `http://localhost:9000`).
- **Bucket MinIO** : `bucket: pyingest-staging`, `region_name: us-east-1`.
- **Métadonnées d'exécution** : `backend: postgres` (PostgreSQL 16).
- **Stack Docker associée** : [docker-compose.staging.yml](file:///Users/awf/workspace/professionnal/webtech/clients/prepavogt-alumni/packages/pyingestkit-v0.6.0/docker-compose.staging.yml).

### C. Profil Production Entreprise : [pyingest.yml.prod](file:///Users/awf/workspace/professionnal/webtech/clients/prepavogt-alumni/packages/pyingestkit-v0.6.0/pyingest.yml.prod)
- **Objectif** : Exécution haute résilience, sécurité stricte des secrets (12-Factor), observabilité conteneurs.
- **Stockage d'artéfacts** : `backend: s3` avec support AWS S3 natif ou Cloudflare R2 (`region_name: auto`).
- **Bucket distant** : `bucket: pyingest-artifacts`, `prefix: production/artifacts`.
- **Métadonnées** : `backend: postgres` avec DSN injecté via `PYINGEST_DATABASE_URL`.
- **Target Warehouse** : Cible PostgreSQL de production configurée (`load_mode: replace`).
- **Journalisation** : `format: plain` (optimisé pour FluentBit, Datadog, CloudWatch, Airflow) + rotation de fichier JSON (10 Mo x 5).

## 2. Qualification Object Storage : MinIO, AWS S3 & Cloudflare R2

### Défi technique : Compatibilité des régions (`InvalidRegionName`)
Lors de l'utilisation de Cloudflare R2 avec le SDK Boto3, spécifier une région AWS classique comme `eu-west-3` provoquait l'erreur suivante :
```text
botocore.exceptions.ClientError: An error occurred (InvalidRegionName) when calling the PutObject operation:
The region name 'eu-west-3' is not valid. Must be one of: wnam, enam, weur, eeur, apac, oc, auto
```

### Solution implémentée
Dans `pyingest.yml.prod` et la couche de configuration `S3ArtifactConfig`, le paramètre `region_name` a été configuré sur `auto` :
```yaml
artifacts:
  backend: s3
  s3:
    bucket: pyingest-artifacts
    prefix: production/artifacts
    region_name: auto                    # 'auto' pour Cloudflare R2 / MinIO, ou région AWS
    endpoint_url_env: PYINGEST_S3_ENDPOINT_URL # URL d'endpoint S3-compatible
    cache_path: .pyingest/cache
```
Cette valeur est universellement acceptée par Cloudflare R2 et MinIO, tout en permettant à AWS S3 de fonctionner avec sa région par défaut injectée via `AWS_DEFAULT_REGION`.

## 3. Stack Staging Automatisée ([docker-compose.staging.yml](file:///Users/awf/workspace/professionnal/webtech/clients/prepavogt-alumni/packages/pyingestkit-v0.6.0/docker-compose.staging.yml))

Pour éliminer toute complexité d'installation en environnement de pré-production ou de test, une stack Docker Compose autonome a été créée :
1. **PostgreSQL 16 Alpine** sur le port standard `5432` avec healthcheck SQL `pg_isready`.
2. **MinIO Server** sur le port `9000` (API S3) et `9001` (Console Web) avec healthcheck HTTP `/minio/health/live`.
3. **MinIO Init (`mc`)** : Conteneur one-shot démarré dès que MinIO est sain, créant automatiquement le bucket `pyingest-staging` sans intervention manuelle.

```bash
# Démarrer la stack de staging complète
docker compose -f docker-compose.staging.yml up -d

# Lancer le pipeline avec le profil staging
pyingest run demo.versioned_s3 --config pyingest.yml.stg --fixture --param revision=1
```
